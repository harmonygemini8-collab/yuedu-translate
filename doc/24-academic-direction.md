## 1. 方向变更

| | 之前（01、21） | 现在 |
|---|---|---|
| 目标用户 | 泛英文网页读者：开发者、学生与研究人员、知识工作者 | **首发楔子：学术论文阅读者**（高校、研究所、留学生），其余用户顺带 |
| 对外卖点 | 保留原文的双语对照；生词连同它在这句话里的意思一起查 | 在此之上加上「**公式不崩、术语不乱、引用与脚注不拆句**」 |
| 优先级 | 网页 → 视频字幕 → 输入框 | **论文网页（arXiv HTML/ar5iv）→ 术语一致 → 表格与参考文献 → PDF** |

选择学术方向的理由（来自方案第三、九节）：场景封闭（论文站点 + PDF）、痛点可量化（公式、术语、表格）、付费意愿相对高。方案同时提醒：术语本身不是它的差异化楔子（对手已有"先分析全文再翻译"），真正拿得出手的是**免费承诺不缩水、长页不卡、自带 Key 全功能、不审查**；学术人群的卖点写成「读论文不卡、公式不崩」。这一点以方案原文为准，本文不展开。

不变的约束：免费层即完整产品；Key 只存本地；账号、同步、团队、支付是服务端能力。**PDF 暂不做**：先把 HTML 论文做到可对外推荐，否则 PDF 只会把同样的毛病原样带过去。

## 4. 已知限制（对外不要承诺的）

- **只在 arXiv 的 HTML 版（ar5iv）上测过**，且是人工在浏览器里看。KaTeX、MathJax 页面按结构支持，没有真实页面验证。
- 占位符靠翻译引擎"原样带回"：谷歌免费接口实测可行，微软与大模型服务理论上也可，**未逐一实测**；偶尔被吞或改坏，已有两层兜底（宽容还原、不带占位符重翻），但极端情况仍会出错。
- 引用在译文里是普通文字，不是可点击的链接。
- 术语锁定只处理「大写开头的多词术语」，且依赖该术语单独翻译一次的结果，这个单独的翻译有时也不准（如 QNLI 那样的缩写不在此列）。
- 朗读译文时，公式的文字也会被读出来。
- 上下标在所有网站一律保留原样，H₂O、10ᵗʰ 之类偶尔会被引擎在周围加空格。
- 全大写的缩写（含 AI、CPU）在整句正文里一律不翻；整句都是大写的标题不受影响。

### 7.0 调研阶段进展（2026-10-30）

用户给了两条明确输入：① 参考竞品「精挑翻译」的文档翻译页（`selecttranslate.com/zhHans/file`：上传 PDF/EPUB/DOCX/TXT/HTML/Markdown/字幕，网页端出译文，另有「PDF Plus」专门应付复杂排版/公式/扫描件）；② **PDF 翻译要放在 `getyuedu.com` 服务器上做，不是扩展内的功能**。这改变了 §7.1 原来"自己做个扩展内阅读页"的假设——方向改成**网页端文档上传翻译**，和竞品的产品形态一致，但实现仍自己的管线，不依赖竞品代码。

拿真实 PDF 做了一轮 `pdf.js`（`pdfjs-dist@4.7.76`）文字提取可行性测试（Transformer 论文原版 PDF，15 页，`arxiv.org/pdf/1706.03762`），结论：

- **阅读顺序比预想的乐观**：原先担心"双栏论文顺序读错"，但实测这篇论文（NeurIPS 排版）**整篇是单栏宽版式**，不是双栏——逐行核对 `getTextContent()` 返回顺序，和人眼阅读顺序完全一致，没有乱序。产品目标用户群（NeurIPS/ACL/ICML 这类 ML/NLP 顶会论文）大多也是单栏排版，双栏主要出现在部分 IEEE 风格的会议论文里。**结论：双栏问题不是首版必须解决的阻塞项，按单栏实现，双栏论文先不保证效果，遇到真实需求再做按坐标聚类分栏**。
- **公式确认会被打散，验证了 §7.3 原先的判断**：真实提取到的公式行，例如 "Attention(Q, K, V) = softmax(QK^T/√d_k)V"，`pdf.js` 把它拆成一串短文本片段（`"Attention("`、`"Q, K, V"`、`") = softmax("`、`"QK"`、上标 `"T"`……），每段都有自己的坐标，但彼此之间没有语义关联，不像 HTML 论文有 `<math>` 标签能整体摘出来做占位符。v1 公式区域大概率要么被当成普通文字送去翻译（引擎把 "softmax" 当单词翻译，排版还会乱），要么要专门写"识别出这是公式行，整行跳过翻译"的启发式（比坐标聚类分栏更麻烦，因为公式可能和正文混在同一行）。**v1 范围建议：公式行整行跳过翻译、保留原样，不追求和 HTML 论文同等的占位符效果**。
- **服务器现状离"能接收文件上传"很远**：`server/app.ts` 当前 `MAX_BODY_BYTES = 64 * 1024`（64KB，为文本翻译请求设计），没有任何运行时依赖（`package.json` 没有 `dependencies`），没有文件存储、没有超时控制之外的大文件处理逻辑。做 MVP 至少要加：`pdfjs-dist` 依赖、一个走更大请求体（或改成流式上传）的上传接口、临时文件的落地与清理、以及大概率要挂上账号额度（整篇论文的翻译成本和现在"选中文字才翻"完全不是一个量级，不能继续无限免费）。

### 7.1 硬约束：不能走"原生阅读器加一层"（扩展侧，已被 §7.0 的方向调整取代，留作记录）

Chrome 自带的 PDF 阅读器（`chrome-extension://mhjfbmdgcfjbbpaeojofohoefgiehjai/`，内嵌的 PDFium）是独立的沙盒环境，不是普通网页，content script 常规途径进不去；[03-prd.md §4](./03-prd.md) 早已把它列进「首版不承诺」。可行的路只有一条：**自己基于 `pdf.js` 做一个阅读页**，把本地或网络 PDF 接管到这个阅读页里打开（类似对手的做法），而不是在用户已经打开的原生 PDF 标签页上做文章。这意味着 PDF 不是给现有管线接一个入口，是三块新东西：

| 新增部分（原设想：扩展内阅读页，已由 §7.0 调整为网页端） | 对应现有模块 | 差异 |
|---|---|---|
| ~~PDF 阅读页（自己的 `pdf.html` + 渲染）~~ → 网页端上传翻译页（`getyuedu.com`） | `website/`（静态页）+ `server/`（API） | 网页端上传 PDF，`pdf.js` 在服务器端提取文字（不是扩展里渲染） |
| 文字与版面提取 | `src/content/extractor.ts`（DOM 树） | PDF 没有 DOM，只有定位的文字块（`pdf.js` 的 `getTextContent`），要自己拼段落、判断标题/正文/表格/公式区域；§7.0 实测：单栏论文顺序可靠，双栏需按坐标聚类（v1 不做） |
| 双语呈现 | `src/content/renderer.ts`（插入旁置节点） | 网页端重新渲染整篇译文（流式双语视图，类似现有网页体验），不追求还原原始 PDF 排版 |
| 文件上传与存储 | 无对应，全新 | `server/app.ts` 现在 `MAX_BODY_BYTES` 只有 64KB、零运行时依赖，上传接口、临时文件落地与清理、超大文档的额度控制都要新建 |

### 7.3 明显会降级的点（先说清楚，不要等用户发现）

- **扫描版 PDF 直接不支持**：没有文字层，等同图片，这是 `pdf.js` 本身的限制，不是我们能解的。
- **公式大概率不翻译，只保留原样**：HTML 论文那套占位符机制靠 `<math>` 标签，PDF 没有对应结构；要做到同等效果需要公式识别（OCR/布局模型），工作量和现有任何一项都不是一个量级，v1 不做。
- **双栏论文 v1 不保证顺序**：2026-10-30 实测 Transformer 论文（NeurIPS 排版）是单栏，`pdf.js` 返回顺序和人眼阅读一致；但 NeurIPS/ACL/ICML 之外的双栏排版（部分 IEEE 风格会议论文）仍可能被按坐标顺序误读，v1 不做按坐标聚类分栏，遇到真实用户反馈再做。
- **网页端重排版，不保留原始版式**：方向已定为网页端整篇重排成双语流式阅读页（§7.0），不做"叠加浮层对齐原文位置"这条路——重排版丢失原始图表位置感，但在复杂排版下更不容易对不齐，体验更可控。
