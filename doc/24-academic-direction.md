## 1. 方向变更

| | 之前（01、21） | 现在 |
|---|---|---|
| 目标用户 | 泛英文网页读者：开发者、学生与研究人员、知识工作者 | **首发楔子：学术论文阅读者**（高校、研究所、留学生），其余用户顺带 |
| 对外卖点 | 保留原文的双语对照；生词连同它在这句话里的意思一起查 | 在此之上加上「**公式不崩、术语不乱、引用与脚注不拆句**」 |
| 优先级 | 网页 → 视频字幕 → 输入框 | **论文网页（arXiv HTML/ar5iv）→ 术语一致 → 表格与参考文献 → PDF** |

选择学术方向的理由（来自方案第三、九节）：场景封闭（论文站点 + PDF）、痛点可量化（公式、术语、表格）、付费意愿相对高。方案同时提醒：术语本身不是它的差异化楔子（对手已有"先分析全文再翻译"），真正拿得出手的是**免费承诺不缩水、长页不卡、自带 Key 全功能、不审查**；学术人群的卖点写成「读论文不卡、公式不崩」。这一点以方案原文为准，本文不展开。

不变的约束：免费层即完整产品；Key 只存本地；账号、同步、团队、支付是服务端能力。**PDF 暂不做**：先把 HTML 论文做到可对外推荐，否则 PDF 只会把同样的毛病原样带过去。

## 4. 已知限制（对外不要承诺的）

- **只在 arXiv 的 HTML 版（ar5iv）上测过**，且是人工在浏览器里看。KaTeX、MathJax 页面按结构支持，没有真实页面验证。
- 占位符靠翻译引擎"原样带回"：谷歌免费接口实测可行，微软与大模型服务理论上也可，**未逐一实测**；偶尔被吞或改坏，已有两层兜底（宽容还原、不带占位符重翻），但极端情况仍会出错。
- 引用在译文里是普通文字，不是可点击的链接。
- 术语锁定只处理「大写开头的多词术语」，且依赖该术语单独翻译一次的结果，这个单独的翻译有时也不准（如 QNLI 那样的缩写不在此列）。
- 朗读译文时，公式的文字也会被读出来。
- 上下标在所有网站一律保留原样，H₂O、10ᵗʰ 之类偶尔会被引擎在周围加空格。
- 全大写的缩写（含 AI、CPU）在整句正文里一律不翻；整句都是大写的标题不受影响。

### 7.1 硬约束：不能走"原生阅读器加一层"

Chrome 自带的 PDF 阅读器（`chrome-extension://mhjfbmdgcfjbbpaeojofohoefgiehjai/`，内嵌的 PDFium）是独立的沙盒环境，不是普通网页，content script 常规途径进不去；[03-prd.md §4](./03-prd.md) 早已把它列进「首版不承诺」。可行的路只有一条：**自己基于 `pdf.js` 做一个阅读页**，把本地或网络 PDF 接管到这个阅读页里打开（类似对手的做法），而不是在用户已经打开的原生 PDF 标签页上做文章。这意味着 PDF 不是给现有管线接一个入口，是三块新东西：

| 新增部分 | 对应现有模块 | 差异 |
|---|---|---|
| PDF 阅读页（自己的 `pdf.html` + 渲染） | 无对应，全新 | 需要接管 `.pdf` 请求或提供"用阅读器打开"入口；渲染用 `pdf.js` |
| 文字与版面提取 | `src/content/extractor.ts`（DOM 树） | PDF 没有 DOM，只有定位的文字块（`pdf.js` 的 `getTextContent`），要自己拼段落、判断标题/正文/表格/公式区域 |
| 双语呈现 | `src/content/renderer.ts`（插入旁置节点） | 固定排版页面插不进去，只能叠加浮层对齐坐标，或整篇重排成类似网页的流式双语视图（重排更像现有体验，但丢失原始版式） |

### 7.3 明显会降级的点（先说清楚，不要等用户发现）

- **扫描版 PDF 直接不支持**：没有文字层，等同图片，这是 `pdf.js` 本身的限制，不是我们能解的。
- **公式大概率不翻译，只保留原样**：HTML 论文那套占位符机制靠 `<math>` 标签，PDF 没有对应结构；要做到同等效果需要公式识别（OCR/布局模型），工作量和现有任何一项都不是一个量级，v1 不做。
- **双栏论文的阅读顺序容易错**：`pdf.js` 按文字块在页面上的坐标返回，不天然知道"先读左栏再读右栏"，需要自己按坐标聚类，arXiv 双栏论文是最常见场景，这个必须在调研阶段就验证，不能留到后面才发现做不到。
- **重排版 vs 保留原版式是二选一，不是都要**：保留原版式（浮层对齐）在复杂排版下对齐误差大、看着不齐，重排版体验更稳但会丢掉原始图表位置感；调研阶段要给个建议，不是都做。
