## 2. 开源（open core）：现状、要点与步骤

### 2.1 现状（2026-10-29 核对）

- 仓库 `harmonygemini8-collab/Yilin-Translate` 是 **私有**（GitHub 显示 PRIVATE），没有 LICENSE。
- 一个仓库里放着所有东西：扩展（`src/`）、服务端（`server/`：账号、管理后台、邮件、套餐、翻译服务商）、官网、`doc/` 全部文档（含公司主体与收款 19、首批用户 20、宣传 21、付费设计 15、服务器部署 16）、`release/`（约 80 MB 的上架素材）。
- **服务端会引用扩展代码**：`server/` 里直接 `import` 了 `src/shared/{messages,settings,i18n}`、`src/content/protect`、`src/background/google-free`。所以拆开后，私有的服务端要能拿到公开的扩展代码。
- 提交历史 192 个，其中 `doc/16-server-deployment.md` 在**所有 16 个版本**里都带着看起来是真实的密钥（见 §2.2）。

### 2.2 先处理，再谈公开：历史里的密钥

在 `doc/16-server-deployment.md` 的示例配置里，有这些值**看起来是真的而不是占位符**：开发令牌、会话签名密钥、Resend 邮件密钥（两个）、OpenAI 密钥、谷歌翻译密钥、硅基流动密钥。`doc/13-website.md` 里还有服务器的公网 IP。它们在 git 历史里，只删当前文件**没有用**。

- **现在就做（仓库仍是私有也要做）**：到各服务商后台把这些密钥作废并重新生成，服务器上换成新值；`YILIN_AUTH_SECRET` 换了会让所有人重新登录，选一个时间做。
- 文档里的示例改成 `<…>` 占位符，只写在新提交里（旧值已作废，才不算泄露）。
- 公开仓库**不带原来的提交历史**（见 §2.4），这样历史里的旧值不会随公开带出去。

说明两点（2026-10-29，与方案 §五之一的表格对照后）：

- 方案里的「引擎适配器：开源」指**扩展里直接调用各家模型的适配器**（用户自带 Key，Key 只存本地）。这一块**还没有**（进度表 §1.1「自带 Key」⬜），做出来后放在公开仓库。`server/providers` 是服务端的翻译服务商适配，带路由、额度和提示词，属于运营层，**闭源**。
- 「账号与同步」要拆开：登录界面、查额度、调用服务器接口的**客户端代码公开**；验证码登录、会话、数据库、同步存储这些**服务端闭源**。

扩展里**账号登录、查额度**这些客户端代码照常公开：它们本来就是用户浏览器里看得到的代码，公开它正好兑现「数据去向可查」。

### 2.5 AGPL 的几个后果，决定前要知道

- 公开的代码你自己保有版权，所以**你自己的服务端和官方发行版可以另行使用同一份代码，不受 AGPL 约束**；AGPL 约束的是别人拿去做网络服务。
- 外部贡献者的代码：没有 CLA 之前，不要合并他人的 PR，否则你对那部分没有完整的授权。
- 依赖库的许可证要查一遍（现在运行时依赖很少，开发依赖不影响）。
- 一旦公开并被人 fork，**不能收回**；已公开的版本永远是 AGPL。
