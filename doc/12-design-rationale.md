# 12 设计思路归档

> 文档编号：DESIGN-001 ｜ 版本：v0.1 ｜ 状态：持续维护  
> 用途：记录“为什么这样设计”。决策结论的一览表见 [10 风险与决策记录](./10-risks-and-decisions.md)；本文补充背景、考虑过的方案和取舍。

## 1. 设计原则

| 原则 | 含义 | 体现 |
|---|---|---|
| 原文为主，译文为辅 | 译文帮助理解，不替代、不遮挡原文 | 译文紧跟在对应段落之后，默认与原文样式一致 |
| 简洁、简约 | 界面只保留完成任务所需的信息，不堆说明文字 | 选择框只显示服务名；不可用选项置灰，不加解释后缀 |
| 如实告知 | 不夸大能力，不隐瞒数据去向与风险 | 隐私说明逐项写明文本发给谁；免费谷歌接口标注“不保证稳定” |
| 可恢复 | 扩展对网页的任何修改都能完整撤销 | “显示原文”只移除扩展自己插入的节点与标记 |
| 成本可控 | 任何会花钱的路径都有硬上限 | 服务器月度预算、按服务字符上限、按需翻译可视区域 |

## 2. 品牌与图标

**当前品牌：阅渡 · 双语对照翻译。**“阅”表示阅读，“渡”表示渡过语言障碍。副标题直接说明产品功能，避免仅凭名称猜测用途。英文展示名使用拼音 **Yuedu Translate**；此前讨论过的 Readora、Bilinea 均未采用。现有宣传语“原文在眼前，理解在身边”继续保留。

**更名记录：**用户确认将旧品牌“译邻 / Yilin Translate”更名为“阅渡”。旧品牌初筛发现同行业同名及近似名称；该初筛仅作历史依据，不能推导新名称可注册或无权利冲突。新名称的商店、商标及域名查重仍待完成（DEC-01）。

**更新范围：**扩展管理页名称、六种界面语言、右键菜单、网页状态提示、官网与隐私政策、商店说明、宣传图片、npm 包名及公开版 ZIP 文件名同步更新。图标不含文字，继续使用现有几何图形。

**兼容性边界：**保留 `YILIN_*` / `__YILIN_*` 配置名、`data-yilin*` / `.yilin-*` DOM 标记、`window.__yilin*` 注入标记、`yilin-toggle` 菜单 ID 和 `yilin-site-lang` 本地存储键。这些是内部协议，不是对外品牌；保留它们可让已有配置、页面清理和语言偏好继续有效。现有 GitHub 仓库地址与 nginx 部署示例路径不自动改名。

**图标设计：**

| 元素 | 设计 | 含义 |
|---|---|---|
| 底 | 圆角方块，青绿 `#14b8a6` → 蓝 `#2563eb` 对角渐变 | 清新、专业，在浅色与深色工具栏上都醒目 |
| 上方两条白色横条 | 一长一短 | 原文段落 |
| 下方黄色横条 + 左侧黄色竖线 | 黄色 `#fcd34d` | 紧挨原文的译文；竖线呼应网页中译文左侧的标识线 |

考虑过的方案：

- 系统默认图标（灰底“译”字）：没有辨识度，用户反馈不好看。
- 用“译”字做图标：直观，但使用系统字体字形做商业标识可能涉及字体授权，暂不采用；如需字形方案，应购买可商用字体或请设计师绘制。
- 采用几何图形：小尺寸（16px）下仍能分辨“白色原文 + 黄色译文”的结构，且无授权风险。

**实现：**`scripts/generate-icons.mjs` 用矢量形状直接生成 16/32/48/128 PNG（`npm run icons`），无图像依赖。128 尺寸按 Chrome 应用商店图片指南留出四周各 16 px 透明边距（图形 96×96），同时输出 `release/assets/store-icon-128x128.png` 供后台“商店图标”上传；16/32/48 用于工具栏，铺满画布以保证小尺寸可辨认；矢量源见 [assets/icon.svg](./assets/icon.svg)。修改设计时同时更新脚本与 SVG。

## 3. 弹窗与设置页

**弹窗只做三件事：**选服务、选语言、控制翻译（翻译 / 停止 / 显示原文 / 重试）。

- 顶部一行状态条说明当前服务的数据去向（例如“段落文本由浏览器直接发送给 Google”），而不是在多处重复隐私说明。
- 进度以“已翻译 N 段 · 失败 M 段”表示，不显示百分比：动态页面会不断出现新段落，百分比会误导。
- 首次使用前在弹窗内确认隐私说明，确认一次即可。

**翻译服务选择框按档位分组：**

```text
免费：谷歌翻译（免费）｜微软翻译（免费额度）
付费：谷歌翻译（官方 API）｜OpenAI（付费）
```

- 分组让用户先看到“免费 / 付费”，再选具体服务。
- 当前构建不可用的服务（需要服务器而未连接）只置灰，不加解释文字，保持简洁；原因写在设置页对应提示和文档里。
- 后续可进一步去掉选项名中的括号说明（分组已能区分），待产品确认。

**设置页：**每个翻译服务一句提示，说明它是什么、额度如何、数据经过哪里。服务器连接区仅在连接后端的构建中显示。

## 3.1 多语言

**目标语言：**44 种，按地区分组并可搜索，完整列表与取舍见 §3.3。

- 语言名称用该语言自己的写法显示（如“Tiếng Việt”），任何界面语言下用户都能认出自己的语言。
- 各翻译服务支持的语言不同，选择框会自动禁用不能搭配的“服务 × 语言”组合，服务器也会拒绝这类请求，避免用户选了却翻不出来。
- 阿拉伯语从右往左书写：译文节点设置 `dir="rtl"`，标识竖线用逻辑属性 `border-inline-start`，在阿拉伯语译文中自动出现在右侧。
- 已经是目标语言的文字不翻译：中文、阿拉伯文按文字类别判断，越南语按其特有字母（ơ、ư、đ 及带声调元音）判断；马来语与英语同为普通拉丁字母，无法可靠区分，暂不跳过。

**界面语言：**简体中文、繁體中文、English、日本語、Tiếng Việt、Bahasa Melayu、العربية，默认“跟随浏览器”，可在设置页切换。

**日语支持（2026-10-11，FR-09）：**复用现有语言目录与选择器，显示自称「日本語」；浏览器 `ja` / `ja-JP` 自动匹配 `ja`，手动选择优先且不改变翻译目标语言。扩展、官网、Chrome `_locales/ja` 与登录邮件同步提供日语，避免从设置切换到官网或登录时语言断层；不增加权限、依赖或翻译服务调用。对应决策见 10 ADR-27，回归测试见 `i18n.test.ts`、`website.test.ts` 与 `server/accounts.test.ts`。本次仅更新本地代码与文案，扩展、官网和服务器均需发布后才在线上生效。

- 弹窗、设置页、右键菜单、网页上的“翻译中 / 失败 / 重试”提示都跟随界面语言；切换后设置页立即重绘，右键菜单同步更新。
- 界面语言与目标语言相互独立：例如越南用户可以用越南语界面，把英文网页翻译成越南语。
- 扩展名称与商店描述按浏览器语言显示（Chrome `_locales` 机制，无法在扩展内切换）。
- 阿拉伯语界面整体切换为从右往左排版。
- 文案集中在 `src/shared/i18n.ts`，以简体中文为源；类型检查保证每种语言键齐全，测试保证占位符一致。**日语、越南语、马来语、阿拉伯语、英语、繁体中文文案为初稿，正式发布前需母语者审校。**

## 3.2 关于与联系方式

扩展里原先找不到官网和联系邮箱：弹窗页脚只有快捷键提示和隐私说明链接，设置页也没有"关于"。
这对用户不合适——装了扩展的人遇到问题、想反馈或想确认是谁做的，手上没有任何出口，只能回商店页去找；
对商店审核也不利，隐私政策要求能看到联系邮箱。

现在三处都给出口，都是只读的一行文字，不额外解释：

| 位置 | 内容 |
|---|---|
| 弹窗页脚 | 在"隐私说明"旁加一个"官网"链接（页脚允许换行，避免 300px 宽度下挤压） |
| 设置页"关于" | 版本号（取自 manifest）、官网链接、联系邮箱（`mailto:`） |
| `manifest.json` | `homepage_url`，Chrome 的扩展详情页据此显示"网站" |

地址集中在 [src/shared/links.ts](../src/shared/links.ts) 一处，与官网的 `website/src/config.ts`、
商店材料 `release/store/listing.md` 保持一致，由 `tests/contact.test.ts` 守住，避免以后换域名只改一边。

## 3.3 目标语言从 5 种扩到 44 种

原先只有简中、繁中、越南语、马来语、阿拉伯语五种，是按首批目标用户选的。
扩到 44 种的理由很直接：翻译服务本身不是瓶颈——Google、微软和大模型都覆盖上百种语言，
我们只是没把它们放进列表；而用户装一个翻译扩展，期待的是"我要的语言在里面"。

44 种的取法是"主流服务普遍支持 + 使用或学习人口大"，按地区分八组
（东亚、东南亚、西欧、北欧、中东欧、中东、南亚、非洲），完整列表见
[src/shared/settings.ts](../src/shared/settings.ts) 的 `TARGET_LANGUAGES` 与 `LANGUAGE_GROUPS`。

三件配套的事：

- **列表长了就得能搜。** 44 行下拉是一次长滚动，所以换成带搜索框的分组面板，
  可按界面语言名（"德语"）、语言自称（"Français"）或语言代码（"pt-BR"）搜索。
  真正的 `<select>` 仍留在 DOM 里持有取值，面板只是覆盖在它上面——这样
  `syncAvailability` 的置灰逻辑和设置保存都不用改。
- **名字不用翻译 44 × 7 遍。** 列表里显示的是 `Intl.DisplayNames` 按当前界面语言给出的名字，
  加上语言自己的写法，形如「德语 (Deutsch)」。以后再加语言只需补它自己的名字，不产生翻译工作量。
- **语言代码各服务写法不同。** 微软的 `pt` 指巴西葡语（欧洲葡语是 `pt-PT`），Google Cloud v2 没有
  `pt-BR`、希伯来语仍用旧式 `iw`，映射表放在各自的 provider 里。现有服务都覆盖全部 44 种，
  但 `ENGINE_LANGUAGES` 这张表保留着：以后接入覆盖面更窄的服务时，缺的语言在列表里**置灰而不是隐藏**——
  隐藏会让用户以为阅渡不支持，置灰则说明是"换个服务就有"。

## 4. 网页内译文呈现

| 决定 | 原因 |
|---|---|
| 译文作为段落内的块级元素，插在段落末尾 | 不改变原文结构，链接、按钮照常可用；列表项、表格单元格中也能正确显示 |
| 嵌套段落（列表中的子列表）译文插在子列表之前 | 译文紧跟它对应的那一行文字 |
| 只用 `textContent` 写入译文 | 翻译结果视为不可信内容，杜绝注入 |
| **默认与原文样式一致，保留左侧竖线**：继承原段落的字体、字号、粗细、颜色、行高，不降低不透明度；左侧一条与文字同色的细竖线标识译文 | 用户反馈：译文应与原文一致（标题译文也应是标题样式），淡化和缩小显得不协调；但需要竖线一眼区分原文与译文。字号、颜色、竖线均可在设置页自定义 |
| 单段失败显示“重试”，不影响其他段落 | 局部失败不打断阅读 |

## 4.1 翻译范围：正文 / 整页

**起因：**用户在 Stripe 后台试用时只翻译了 3 段——菜单、标签页、表单标题、按钮都被正文规则过滤。正文规则为阅读文章设计，用在应用界面上覆盖不足。

| 决定 | 原因 |
|---|---|
| 新增“整页”模式，**“正文”保持默认且行为不变** | 文章阅读仍是主场景，正文模式的 30 页评测基线（精确率 99.7%、召回率 100%）不受影响；用户按需切换 |
| 范围选择放在弹窗，与目标语言并列 | 是否翻译界面文字因网站而异，需随手切换；不放进设置页深处 |
| 整页模式纳入菜单、标签页、按钮、表单标题、提示条；仍不读取输入框、代码、隐藏内容 | 界面文字是理解后台页面所需；表单值可能是个人数据，任何模式都不读取 |
| 界面文字（40 字以内的菜单、按钮、表单标题、短标题）译文**同一行内联**显示（“Home 首页”）：放进承载文字的最内层元素末尾，0.9 倍字号、无竖线、不换行 | 首版把译文作为块元素插入菜单项，而菜单项多为横向弹性布局，译文成了被挤压到最窄的子项，中文被压成一字一行并溢出到下一项（用户在 Stripe 侧栏实测）。内联到文字所在元素后行高与对齐不变 |
| 40 字以上的文字即使在侧栏、页眉中也按正文块显示 | 长句内联会撑宽界面，且不换行会溢出 |
| 切换范围立即重新翻译 | 与切换翻译服务一致，避免页面上同时存在两种范围的结果 |

**限制：**整页模式暂无标注评测集，复杂应用（虚拟滚动表格、画布绘制的界面）可能仍有遗漏或布局变形；需真实站点抽查后补充测试页面。

## 4.2 划词查词

整页翻译解决"这篇文章讲什么"，但读双语的人还有另一个动作：读到一个词卡住了，想知道它在**这句话里**是什么意思。
查词典能给出一串义项，查不出该选哪个；机器翻译给出一个结果，看不到为什么。所以这里给的是两者之和：
音标、常用义项，再加一句"在这句话里"的解释。

几个决定和它们的理由：

| 决定 | 理由 |
|---|---|
| 选中后出按钮，点击才翻译 | 选中即弹会打断复制、拖选和边读边划；也会在用户没有意图时消耗额度。业界主流扩展同样用这一步 |
| 单词给词条，整段只给译文 | 一段话没有"音标"和"词性"可言；强行套词条格式只会制造空字段 |
| 词条限 VIP，免费用户给译文 | 词条每次都要调大模型，而预算上限是 $10/月（`YILIN_MONTHLY_BUDGET_USD`）。免费用户仍拿得到译文和朗读，气泡底部说明差在哪，而不是报错或留白 |
| 全文朗读按结构选正文，不按字数 | 字数阈值会误删短标题、放过长的导航文字。改为：先取 `article`/`main` 中译文最多的容器，再排除其中的 `nav/aside/footer/a/button/time/figcaption` 等页面杂项，保留 `<article><header>` 里的标题。逐段（再切成≤160字的短句）排队，因为 Chrome 在线语音读长文本约 15 秒会自行中断。声音自动选带 Natural/Neural 的；没有时用系统默认，Edge 的 Natural 声音明显更好 |
| 仅译文用「原文字号归零」而不是隐藏节点 | 原文常是裸文本节点，CSS 隐藏不了；`font-size: 0` 既让它不占空间，又保住段内的图片、图标与布局。代价是译文要自己接管字号：渲染时读出段落原本的字号、行高与上下外边距（外边距若写成 em 会随字号变成 0，故转成像素），存在译文节点上。只对「译文已完成」的段落生效，加载中和失败的保持原文，避免等待时整段空白 |
| 查词气泡逐字出现，但先占好位 | 逐字出现让「正在查」有可感知的反馈。直接边打边插入文字会让气泡一路长高、反复换行；所以每段文字拆成「已显示」与「未显示」两部分，后者 `visibility: hidden` 仍占位，最终版式从第一帧就定了。约 1 秒打完，与长度无关；尊重系统的「减少动态效果」 |
| 息屏朗读只有服务器声音可靠，系统声音被打断时原地等待 | 真机日志证实：页面进入后台时浏览器**取消**系统语音（`interrupted`），后台中不能启动新的（`synthesis-failed`）；服务器声音当作真正的音频播放，息屏不断。曾误以为是页面被冻结，改成触屏整块朗读，日志证明不对，已撤销（整块反而让断点更粗）。所以：系统声音被打断时不往下读，等页面回到前台再重读被打断的那一句，不丢内容；后台里不自动滚动；触屏开始朗读时提前翻译本篇剩余部分（上限约 2 万字），因为息屏后页面不再滚动，翻译不会再被触发。媒体会话加近静音循环对服务器声音有帮助，对系统语音无用，保留是为了锁屏上有暂停键。息屏朗读需要登录，这点要在界面或说明里讲清楚 |
| 朗读跟随页面，但只到本篇文章末尾 | 「读到哪翻到哪」只翻译屏幕附近的段落，所以读完已译部分就读不下去了，需要把页面往下推。但推到页面底部会读进下一篇文章（相关推荐、无限滚动），还会把它们也翻译，白白消耗额度。所以：开始朗读时按「屏幕上第一段所在的 article」锁定文章（不是字数最多的那篇，后者在多篇并排时会选错），最后一次滚动只滚到该容器底边。没有容器可界定时宁可不滚，也不猜。读者自己滚动后让出 4 秒，不与手争页面 |
| 悬浮按钮：触屏才默认出现，主按钮只做一件事 | 手机没有快捷键、右键菜单和悬停，工具栏弹窗也不易点到，没有页面内入口就几乎用不了。主按钮只在「翻译」和「显示原文」之间切换，图标表示点一下的结果；其余动作放进「⋯」展开的大号胶囊，避免一个小圆球上塞多个手势（长按、双击在不同浏览器里不可靠）。电脑上有快捷键，默认不出现，免得遮挡页面。它和查词一样要内容脚本在场，所以在触屏弹窗里提供一键的「所有网站」授权 |
| 查词要在所有页面可用，必须有「所有网站」授权 | 查词气泡由内容脚本绘制，而脚本只在「点过翻译」或「已授权的自动翻译网站」上存在。没有主机权限就无法在用户点击前注入，这是 `activeTab` 的边界，不是 bug。所以「允许在所有网站上运行」开启后，把内容脚本注册到所有页面（`autoScriptMatches`）；脚本只有在自动翻译名单里的网站上才会自己开始翻译，注册到所有页面不会让任何页面自动翻译。设置页在未开启时提示并给出一键开启，不静默申请宽权限 |
| 查词按钮悬停 0.15 秒即开气泡 | 去掉一次点击。延迟是为了鼠标路过按钮不误触发：每次查词都可能消耗 VIP 额度。点击保留，触屏没有悬停 |
| 朗读：本地自然语音优先，其次服务器，最后本地普通语音 | Edge 自带的神经语音免费、不经过我们的服务器、不占额度，所以浏览器已经有就直接用；Chrome 没有，才向服务器要 Azure 的同一批声音。这样 Edge 用户几乎不消耗每月 50 万的免费额度。服务器声音一出错就退回本地，用户不会没声，只会声音变差。音频用 Web Audio 播放而不是 `<audio>`，避免页面的 media-src 策略拦截；新权限（offscreen）会触发重新审核，这一版不加。逐句预取后面两句，句间不停顿 |
| 单词 🔊 朗读用浏览器内置合成（「朗读译文」的规则见上一行） | `speechSynthesis` 本地发声：零成本、不联网、不需要新权限、覆盖系统装了的所有语言。真人发音音质更好，但要接第三方词典 API——新增主机权限、改隐私政策和商店材料，且基本只有英语覆盖得好。等有用户反馈再评估 |
| 气泡放在 Shadow DOM | 页面 CSS 五花八门，普通元素会被改得面目全非；shadow root 隔离样式，译文仍只用 `textContent` 写入 |
| 把所在句子一起发给模型 | 没有上下文就只能给词典义项，"在这句话里"这一条就没了。句子取自选区所在的块级元素，上限 600 字符，围绕选区截取而不是从头截断 |

降级链是：单词 → 大模型词条；失败且原因是未登录 / 非 VIP / 未配置 / 额度用尽 → 普通译文；
其它错误（网络、限流、服务故障）照常报错。这样气泡几乎总有内容可显示。

## 4.3 官网推广调整：先读懂功能，再选择服务

2026-10-11 用户已确认采用本地预览版本，尚未部署线上。官网结构与后续素材计划见 [13 §3.1–§3.2](./13-website.md)：

| 决定 | 原因 |
|---|---|
| 首屏只保留安装与效果示例，VIP 申请入口移到服务卡片 | 免费安装和申请 VIP 是两件事，避免让访客以为安装必须获邀 |
| 双语阅读、划词查词作为两张重点卡片，语言列表默认折叠 | 优先展示阅读场景，不用 44 种语言长列表打断浏览；列表仍可展开、无脚本也能查看 |
| 查词卡片直接标明 VIP 词条权益 | 不让用户把音标、释义和上下文解释误认为全都免费 |
| 不在静态首页承诺固定额度，指向账号页并说明平台共享上限 | 后台可调整额度，仓库默认值不代表线上实际权益；不保证任意长文一次翻完 |
| 注册限制用条件说明，VIP 明确为邀请试用、尚未开放购买 | 未读取线上注册开关，不猜测所有账号都开放或全部需要邀请 |
| 六种语言同步去掉绝对准确、瞬间完成等表述 | 模型可能出错，网络和限流会影响速度；保留原文供核对 |

**越南语宣传片（2026-10-11）：**用户要求单独文案与明快节奏，采用约 35 秒、先结果后操作的结构，避免安装教程和长品牌开场消耗注意力；旁白短句与卖点标题分开，给英越段落留出阅读时间。首版只展示基础查词，避免把 VIP 权益混入免费体验。字幕为预排而非实时速度承诺，服务等待超出镜头时调整时长或标明缩短等待。独立文案与制作状态见 [13 §3.3](./13-website.md)。成片采用深色背景、左侧短标题与右侧实操特写，字幕放在画面下方独立区域，避免盖住查词气泡；以真实源帧合成 1080p 视频，保留源时间戳并明确不是原生 30 fps 全桌面录像。越南语合成女声只发送公开文案，轻配乐本地合成，避免引入不明来源音乐；发布前另做母语与语音商用条件复核。

## 4.4 全球宣传视频：语言与清晰度

2026-10-11 用户否定无声中文初版，要求配音、配乐、字幕、2K 与全球通用展示。采用英文界面和英文合成旁白，以英译西班牙语展示跨语言阅读，不将中文设为唯一目标市场。主版采用可选择的七语言字幕，另导出内嵌英文字幕版，分别适合 YouTube 与静音社交传播，避免七种语言挤在同一画面。

2K 按常用 QHD 规格 2560×1440（16:9）制作；重新采集高像素密度源帧，字幕和标题在成片分辨率绘制，不放大旧成片。实际扩展输出保留，镜头剪辑和定格明确标记为演示剪辑，不制造即时翻译的速度承诺。配乐本地合成，人声段压低音乐；合成配音的商用条件、发音及非英文字幕仍需发布前复核。制作状态见 [13 §3.4](./13-website.md)。

## 4.5 YouTube 封面：缩小后仍能看懂

2026-10-11 为全球视频制作两版英文封面。A 用“READ IN TWO LANGUAGES”说明双语阅读，B 用“TRANSLATE. KEEP THE ORIGINAL.”突出保留原文；大字高对比，配自有图标及已有真实录制画面，不借无关热点、人像或夸张收益吸引点击。

封面不照搬视频整帧的小字幕，重点文字在 320×180 预览下也要可辨；右侧实操画面用于说明功能，不要求推荐列表里读清每个段落。高清图按当前 YouTube 建议提供 3840×2160 JPG，同时给 1280×720 备选，均控制在 2 MB 以下；封面尺寸不改变 2K 视频本体。两版只是设计备选，未做真实流量 A/B 测试。上传文案明确合成配音、剪辑和免费服务限制，避免封面、视频与产品可用功能不一致。交付见 [13 §3.5](./13-website.md)。

越南语 35 秒版本单独使用「ĐỌC SONG NGỮ」大字与「ĐỐI CHIẾU ANH–VIỆT」副标题，明确双语对照阅读而不是只强调机器翻译。右侧仅裁切、等比例缩放真实英越对照源帧，不重新绘制翻译文本；320×180 小图检查主标题可辨，右下角留出播放器时长标记空间。上传包保留该片自己的 35 秒字幕，明确烧录字幕与 YouTube CC 可能叠加，避免误用英文国际版的 45 秒字幕；简介不硬塞不足 10 秒的镜头章节。交付见 13 §3.3。

## 5. 正文识别

- **只翻译主内容区域：**有 `main`/`article` 时只处理其中内容，避免翻译导航、侧栏、页脚；主内容区域文字过少时回退整页，防止误判漏翻。
- **用规则而非机器学习：**规则可解释、可测试，原型阶段足够；用 30 个标注页面做回归评测（精确率 99.7%、召回率 100%，存在过拟合风险，需真实网站抽查）。
- **先补测试页再改规则：**每发现一类误判，先加入标注页面，再调整规则，保证改进可度量、不回退。

详细规则见 [05 系统架构设计 §4](./05-architecture.md)。

## 6. 翻译服务分层

```text
免费档
├─ 谷歌免费接口（浏览器直连，默认）   无需密钥和服务器；非官方，不保证稳定
├─ 微软翻译 F0（经服务器）             官方，每月 200 万字符，用完即停不扣费
付费档
├─ 谷歌官方 API（经服务器）
└─ OpenAI（经服务器，默认 gpt-6-luna）
```

关键取舍：

1. **谷歌免费接口放在浏览器而不是服务器：**所有用户经同一服务器 IP 调用会很快被谷歌限流；浏览器直连分散到各用户自己的网络。代价是用户需能访问 Google，且共享代理 IP 也可能被拒（2026-10-01 实测 429）。
2. **官方 API 一律经服务器：**API 密钥放进扩展等于公开，任何人都能提取盗用。
3. **免费额度由平台共用：**三家官方免费额度合计约每月 300 万字符，用户量增长后需配合单用户额度或失败自动切换。
4. **切换翻译服务立即重新翻译：**已显示的译文属于旧服务，保留会让用户误以为新服务出了问题（曾实际发生：切到谷歌后页面仍显示模拟译文）。

费用与风险细节见 [11 翻译服务与费用控制](./11-translation-services.md)。

## 7. 稳健性

| 场景 | 设计 |
|---|---|
| 扩展重新加载或更新后，页面里残留旧脚本 | 新脚本检测到旧实例已失效（`runtime.id` 为空）时清理其译文并接管；旧实例停止调用扩展接口，不再报错（曾实际发生 “Extension context invalidated”） |
| 弹窗多次注入脚本 | 存活的实例被复用，不重复注册监听 |
| 页面跳转或段落内容变化 | 结果按会话代次与文本指纹校验，过期结果丢弃 |
| 页面框架重渲染段落、抹掉已插入的译文 | 译文文本随段落一起记住；重扫发现译文节点不见了就直接重绘，不重新翻译（某新闻站在滚动时持续重建段落，导致大量段落停在「已翻译」却无译文） |
| Service Worker 被浏览器回收 | Worker 无状态，状态保存在页面与服务器 |
| 设置页只保存用户实际修改的项 | 避免把“显示中的服务”误写成用户选择（曾导致升级后一直使用模拟翻译） |

### 7.1 翻译进度：读到哪，翻到哪

译文按视口推进，只翻译即将看到的段落（`IntersectionObserver`，`rootMargin: 1500px`，约两屏）。

| 取值 | 后果 |
|---|---|
| 过小（初版 600px） | 快速滚动时眼前会出现尚未翻译的段落，读者以为坏了 |
| **1500px（当前）** | 滚动中基本不会撞见未翻译的段落；一篇 247 段的长报道仍只翻读到的部分 |
| 整页一次性翻译 | 没有等待感，但长文一次吃掉大量额度（免费账号每日 2 万字符可能一篇见底），且多数内容读者并不会读到 |

调度不只依赖 `IntersectionObserver`：观察器永远不会报告“被观察时尺寸为 0”的元素，真实文章上出现过 232 段中仅 53 段被翻译、其余停在未排队状态。现在以观察器为快路径，另有一个按滚动节流（250ms）的位置兜底扫描，把落在同一范围内却被漏掉的段落补入队列。

选 1500px 是在“看不见等待”和“不为没读的内容付费”之间取中。免费谷歌翻译没有成本差异，但同一套调度也服务于按字符计费的 VIP 服务，所以不做成整页翻译。

## 9. 邀请制下的登录提示（2026-10-11）

宁可明确拒绝，也不要让人空等。未受邀的邮箱在「发送验证码」这一步就被拒绝并给出申请地址，而不是先寄一封用不了的验证码、等对方输入后才说不行。换来的代价是暴露「这个邮箱是否受邀」，在邀请制内测期间可以接受；开放注册后该检查自动失效。详见 [18 §4.1](./18-invite-operations.md)。

## 10. 视频字幕翻译（2026-10-17，FR-19）

### 10.1 为什么先做字幕轨，而不是语音识别

要看的外文视频绝大多数本身带字幕：YouTube 的人工／自动字幕、公开课、技术大会录像、新闻站的 video.js 播放器。拿到的是**现成的文本和时间轴**，只需翻译和叠加：免费档就能用，一小时演讲约 5–6 万字符，微软免费额度（200 万字符／月）完全够。

语音识别是另一回事：Azure 语音转文字约 **$1／小时音频**，服务器预算硬上限 $10／月，意味着全平台每月只够 10 小时；还要 `tabCapture` 这个高敏感权限（审核更慢、吓退用户）和 MV3 的 offscreen document。因此 ASR 不进免费档，留作 VIP 的按分钟额度功能，等真的收到「这个视频没字幕」的反馈再做。

DRM 平台（Netflix、Disney+ 等）字幕在加密流里，**不支持**，也不尝试。

### 10.2 两类播放器，一条管线

| 播放器 | 取字幕的方式 | 翻译时机 |
|---|---|---|
| 提供 `TextTrack`（标准 `<track>`、hls.js 等） | 把轨道设为 `hidden`——浏览器照常解析出全部 cue，但不自己绘制 | **整轨一次译完**，播放时零等待 |
| 自绘字幕（YouTube、video.js、JW、Shaka 等） | `MutationObserver` 盯住字幕容器 | **逐句即时**，按原文缓存，重复句子不重复花钱 |

两者都归一到同一个 `CueFeed` 接口，翻译、缓存、绘制只写一遍；测试用假的 feed 驱动，不依赖真实播放器。

### 10.3 为什么自己画，而不是改播放器的字幕

把译文塞进播放器自己的字幕节点，等于和每个播放器的样式与重绘逻辑打架，而且它随时会把我们的节点冲掉。改为**按视频的 `getBoundingClientRect()` 定位一层自己的叠加层**：不需要任何播放器配合，样式统一，移除时页面干净。全屏时只有全屏元素的子树会被绘制，所以叠加层会移进全屏元素里。

### 10.4 失败和重复的处理

- 某一句翻译失败：**保留原文**显示，不留空行；并记为「已尝试」，否则每次重绘都会重新请求，一部片子能把额度烧光（第一版就踩过这个无限重绘的坑，由测试发现）。
- 切换目标语言：清空缓存和「已尝试」记录，失败过的句子在新语言下重新来过。

### 10.5 第一次实测后的三处修正（2026-10-17）

实测（带 CC 的网页播放器）暴露三个问题：

1. **原文出现两次**。播放器画了一遍自己的字幕，我们又画了一遍原文。现在凡是我们接管的播放器，它自己的字幕容器一律隐藏（`data-yilin-captions-off`），停止时恢复。注意两种情况都要处理：自绘字幕的播放器，以及**有字幕轨但用自己的渲染器**的播放器（video.js 这类）——后者即使把轨道设成 `hidden`，它仍然会自己画。
2. **译文时而上下、时而并排**。原来每行是 `inline-block`，两行短句就会排到同一行，读起来像一句话。改为每行独占一行（`display: block` + `width: fit-content` + 居中）。
3. **位置不可控**。不同网站的播放器在画面下方放的东西不一样（控制条、台标、原字幕），固定位置总会挡住什么。现在整块（原文 + 译文）可以用鼠标拖动，偏移量记在 `chrome.storage.local` 的 `subtitleOffset`，下次打开还在那儿；`resetPosition()` 可以归位。

另外新增两个设置项 `subtitleColor` / `subtitleBackground`：字幕译文的文字色与底色块颜色。写进样式表前只接受 `#rrggbb` 形式，避免把任意字符串拼进 CSS。

**已知限制**：自绘字幕的播放器必须先点开 CC，我们才拿得到文字——它在关闭状态下根本不往 DOM 里写字幕。有真正字幕轨的播放器不受此限制（轨道设为 `hidden` 即可取到全部 cue）。

### 10.6 自动字幕（YouTube）：等它写完再翻（2026-10-17）

YouTube 的自动字幕是**逐字滚动**的：每多识别出一个词就重写一遍当前行。按「字幕变了就翻译」处理会同时坏三件事——按词发请求（烧额度）、译文一闪而过、半句话的译文本来也没意义。

现在的做法：

- 译文等字幕**停止变化 300 ms** 之后翻译；连续说话几乎没有停顿，所以**最长等 800 ms**，之后无论字幕是否还在变都翻译当前内容（只等安静会让字幕落后画面好几秒，2026-10-20 实测）。
- **原文和译文成对出现**：原文不再逐字抢跑，等这句的译文回来后两行一起显示（2026-10-20 实测原文先跑、译文滞后，看起来不同步）。翻译失败时只显示原文。原文与译文共用设置里的字幕底色。
- 新句子正在说的时候，**这一对（原文+译文）留在屏幕上**，不留空行、不闪；字幕整体消失时才清掉。
- 迟到的结果会被丢弃：如果在等待期间又有新句子定型，只认最新那句。

另外两个同一批发现的问题：

- **缩略图自动播放**。YouTube 首页鼠标划过缩略图就会播放，那也是一个 `<video>`。我们曾经接到它上面，结果叠加层按一个很窄的盒子排版，变成页面边上一列「一个词一行」的竖条。现在**宽度小于 240 px 的播放器一律不接管**。
- **叠加层不跟随**。播放器会随滚动、缩放、全屏和站点自己的吸顶小窗移动。现在在 `scroll`（捕获阶段，站点内部滚动容器也算）、`resize`、`fullscreenchange` 和视频的 `timeupdate` 上重新定位。


### 10.7 YouTube 字幕：读播放器下载的字幕文件，按时间码同步（2026-10-20）

§10.6 的做法是读屏幕上已经出现的字幕、停稳后再翻，无论怎么调短等待，译文都比画面晚（实测原文和译文都落后好几秒）。要真正同步，只能在字幕出现之前就把整份译好，播到哪句显示哪句。

- **拿不到字幕文件**：直接请求字幕地址、或把播放器自己的请求原样重放，返回都是 200 但内容为空——YouTube 要求播放器专属的令牌。能拿到的只有**播放器自己下载时的响应**。
- **做法**：往页面自己的 JS 环境（`world: 'MAIN'`）注入 `caption-hook.js`，包装 `fetch` / `XMLHttpRequest`，只在地址是 `/api/timedtext` 时把响应副本用 `postMessage` 交给内容脚本。其它请求一概不看，也不向任何地方发送。注入走 `scripting.executeScript`，不需要新权限（仍是 `activeTab` / 已授权站点）；由内容脚本发 `CAPTION_HOOK` 消息请后台注入（Firefox 128+ 支持 `world: 'MAIN'`，最低版本 140）。
- **解析**（`timedtext.ts`）：人工字幕一个事件就是一行，自带起止时间；自动字幕（`kind=asr`）逐词带发声时间，按句末标点、停顿 1.2 秒、两行长度（110 字符）、7 秒上限切成句，用词的真实时间当字幕时间。真实数据核对过：逐词偏移 `tOffsetMs`、`\n` 分行事件、开头无文字的窗口事件。
- **同步**（`timed-feed.ts`）：整份提前翻，从播放位置开始、近的先翻；每 100 ms 对照 `video.currentTime`，到点直接显示已译好的一对，没有网络等待。字幕关掉（`.ytp-subtitles-button` 的 `aria-pressed=false`）就不显示；播放器换了下一个视频（地址里的 `v` 不同）时旧字幕作废。
- **已经开着字幕时**：播放器只在打开字幕时下载一次，钩子装得晚就错过了。1 秒内没收到字幕就把字幕按钮关了再开一次，让播放器重新下载（页面上会闪一下）。
- **兜底**：没有字幕轨、钩子没装上、或解析失败时，仍走 §10.6 的读屏幕方式。
- **页面可以伪造这条消息**：它和页面里的其它文本一样不可信，只当文本解析、翻译、`textContent` 显示；解析器对非法结构容错。
- **顺带修的老问题**：字幕按 40 句一批提交，而后台一次最多收 16 句、4000 字符，超了会被整批拒绝（字幕轨一次提交整份文件时也受影响）。现在按这两个限制分批。

隐私政策与商店文案要跟着核对：这是**读取网页自己的网络响应**，内容只在本机解析，需要翻译的字幕文本照旧只发给翻译服务（和页面文字同一路径）。

### 10.8 YouTube 播放器里的阅渡按钮（2026-10-20）

字幕翻译原本只能从工具栏图标或弹窗里开，离看视频的人很远。现在在 YouTube 播放器右下角控制栏（`.ytp-right-controls`，设置按钮前面）放一个阅渡自己的按钮，点一下弹出菜单，参照 YouTube 自己的设置菜单和常见翻译扩展的字幕菜单，**只放我们已有的功能**：

- **开启字幕翻译**：只开关字幕翻译，不动整页翻译（页面的「显示原文」仍会一并停掉字幕）。
- **字幕显示类型**：双语对照 / 仅译文（和弹窗里的开关是同一个设置）。
- **译文字体颜色、字幕底色**：就是设置页那两项，选完关掉取色器才保存，不会拖一下存一次。
- **恢复字幕位置**：把拖走的字幕块放回画面下方。

没有放的：请求 AI 字幕、下载字幕、字体大小与粗细、译文在原文上方还是下方——我们没有这些功能，菜单里不放占位。

实现（`youtube-menu.ts`）：按钮在页面里、菜单在播放器里的 shadow root 中（全屏时可见，页面 CSS 影响不到），文字一律 `textContent`；菜单里的点击和按键都不向上冒泡，否则会触发播放器的暂停和快捷键；播放器切下一个视频会重建控制栏，所以用节流的 `MutationObserver` 在按钮消失时补回去。只在 `youtube.com` / `youtube-nocookie.com` 出现。

### 10.9 YouTube 广告前后的字幕（2026-10-20 实测）

- **广告期间不显示**：广告和正片是同一个 `<video>`，播放时间被广告占用，按时间码取字幕就把正片的字幕画到了广告上。播放器带 `ad-showing` / `ad-interrupting` 类时一律不显示，广告结束自动恢复。
- **广告结束后出现两份原文**：YouTube 每次广告后会重建自己的字幕容器，我们隐藏的是旧容器，新容器显示着播放器自带字幕，和我们画的原文上下各一份。现在字幕源记住自己隐藏的容器（`CueFeed.host`），容器离开页面时按新容器重新建源并隐藏。

### 10.10 手机网页版 YouTube（m.youtube.com，2026-10-21 在 Firefox 安卓版实测）

手机站和电脑站用同一个播放器类（`.html5-video-player`、`.ytp-caption-window-container`），但**控制栏完全不同**，电脑端的几处假设在手机上都不成立：

- **控制栏不在播放器元素里**：在 `ytm-watch-player-controls` 下的 `.player-controls-top`，依次是自动播放开关、`yt-closed-captions-toggle-button`（里面的 `button.ytmClosedCaptioningButtonButton`，`aria-pressed` 表示字幕开关）、设置按钮。阅渡按钮放在 CC 按钮后面，用朴素的 44 px 触控按钮样式（手机栏没有为陌生按钮准备的样式）。菜单在手机上用 `fixed` 定位，从按钮往下展开；全屏时挂到全屏元素里。
- **字幕开关**：`captionsEnabled` 和重新请求字幕文件用的 CC 按钮，原来只认电脑端的 `.ytp-subtitles-button`，手机上找不到就当成「开着」，所以没点 CC 也会显示译文。现在两种按钮都认。
- **播放器自带字幕又冒出来、逐字出现**：播放器会为每一行重新建字幕元素，只给其中一个元素加隐藏标记，新建的会闪现。现在在根节点加标记，再用样式表按选择器（`CAPTION_SELECTORS`）隐藏，不依赖具体元素。
- **整页翻译把播放器字幕又翻了一遍**：竖屏时播放器自带字幕被当成页面文字翻译，在黑底原文下面多出一行带竖线的译文，和我们自己画的绿色字幕重复。现在 `ytp-caption-window-container` / `caption-window` 不参与整页翻译。

### 10.11 其他网站的视频：悬浮在画面右上角的阅渡角标（2026-10-21）

YouTube 有自己的控制栏，我们把按钮放进去（§10.8、§10.10）；别的网站的播放器各有各的控制栏结构，逐个去适配不现实，也容易放错位置。所以对其他网站不碰它的控制栏，改成**悬浮在视频画面右上角的一个小圆形角标**：

- **什么时候出现**：鼠标移到（或手指点了）一个有字幕可读的视频上才出现，停止移动 2.5 秒后消失；打开菜单时不消失，点别处、按 Esc 关闭。宽度小于 240 px 的视频（缩略图、预览）不出现。
- **什么叫「有字幕可读」**（`SubtitleTranslator.hasSource`）：视频带 `subtitles` / `captions` 文字轨，或者所在播放器里有已知的字幕容器（`CAPTION_SELECTORS`）。不用先点「翻译」，所以角标可以直接开启字幕翻译。烧在画面里的字幕没法读，那样的视频不会出现角标。
- **菜单**：和 YouTube 里是同一个（`subtitle-panel.ts` 的 `buildPanel`）：开关字幕翻译、双语/仅译文、译文颜色与底色、恢复字幕位置。YouTube 的按钮和这个角标共用它，不会各改各的。
- **实现**：角标在 shadow root 里，`fixed` 定位，每次鼠标移动最多每 150 ms 找一次视频；全屏时挂进全屏元素；随滚动、缩放重新定位。YouTube 域名上不创建（那里用控制栏按钮）。
- **「有字幕可读」要收紧（2026-10-21 实测）**：一家新闻网站的 video.js 播放器有 `.vjs-text-track-display`，但视频**没有任何字幕**（没有字幕轨、没有字幕文件请求、播放器里没有 CC 按钮）；别家扩展给它加的是语音识别的「AI 字幕」。原先只要有这个空容器就算有字幕，于是角标出现了却翻不出东西。现在要求：有字幕轨，或者字幕容器里**真的出现过文字**（出现过就记住，两句之间容器暂时为空也不影响）。代价是播放器字幕默认关着的网站，要先开字幕、字幕出现后才有角标。没有字幕的视频，我们不做语音识别（要服务器和费用，当前没有）。

**实测补记（2026-10-21，Bloomberg 竖版视频，video.js 播放器）**：

- 角标出现了，开启字幕翻译却没有任何效果。查下来这个视频**没有字幕**：`textTracks` 为空，播放器里没有任何字幕文字，也没有 `.vtt`、字幕播放列表或字幕接口的请求；播放器自带的 `.vjs-text-track-display` 是个空容器。截图里能看到的双语字幕是别家扩展自己画上去的，它靠的是 **AI 字幕**（对声音做语音识别），不是读字幕文件。
- 所以「有字幕可读」的判断收紧了（`SubtitleTranslator.hasSource`）：必须有 `subtitles` / `captions` 文字轨，或者播放器的字幕容器里**真的出现过文字**。一个空容器什么也证明不了，过去把它当成字幕来源，角标才会出现在没有字幕的视频上。
- **AI 字幕（语音识别）暂缓**，评估记录：做法是页面里截取视频声音、分段发服务器识别、再翻译，适合放进 VIP。代价有三：音频要上传（隐私政策与两家商店的数据披露要新增「音频」，审核风险大）；跨域视频和有版权保护（DRM）的视频浏览器不让截声音；字幕会比画面慢约 5 到 10 秒，且每分钟视频都有识别与翻译费用，要按额度限量。要做之前需先定：识别服务与每月预算、是否先邀请制内测、隐私与商店说明怎么写。

## 11. 验证码邮件（2026-10-22）

原来是一段纯文本，看起来像垃圾邮件，也不像正规服务发的。改成大公司常见的样式（参照 Meta 的登录码邮件）：

- **一栏居中、只有一件事**：顶部图标和名字、一条细线、一句说明、「登录验证码」小标签、灰底大号等宽字体的验证码、有效期、「不是本人操作可忽略」、细线、页脚灰色小字。没有按钮、没有营销内容：这封信只为了让人把 6 位数抄过去。
- **页脚写明发往哪个地址、为什么会收到**：让收件人一眼判断是不是自己申请的，也是防钓鱼的常见做法。
- **HTML 与纯文本同时发**：不显示 HTML 的客户端看到整齐的纯文本；只有 HTML 没有纯文本的邮件更容易被判为垃圾邮件。
- **只用表格和内联样式**：多数邮箱客户端会丢掉 `<style>` 和外部样式表。
- **图标用官网的 `icon.png`**：邮件里不内嵌图片（体积大、部分客户端不显示）；客户端拦截图片时，旁边的名字照样表明发件方。
- **地址按文本转义**：邮件里出现的用户地址不能被当成标记解析。
- **阿拉伯语从右到左**，但验证码本身保持从左到右，否则数字顺序在部分客户端里会被翻转。
- 颜色沿用 `ink`、`muted`，新增两个邮件专用的浅色（`mail-line`、`mail-code-bg`），已登记在 [22 §2.2](./22-visual-identity.md)。


## 12. 悬浮按钮在 Firefox 安卓版上"用一次就消失"（2026-10-25）

现象（AMO 正式版复现，不是临时安装才有）：授权「允许在所有网站上运行」后，悬浮按钮只在点过弹窗「翻译」的那一个页面出现；换一个页面、或者回退上一页，又没了。

根因：持久的 `registerContentScripts` 注册只挂在 `onInstalled`、`onStartup` 和权限变化这几个事件上。这几个事件只覆盖"全新安装"和"浏览器本身启动"——不覆盖"后台脚本自己被系统回收、又因为别的原因被重新拉起"，而这恰恰是 MV3 的常态，在 Android 上尤其频繁（系统为省内存会直接杀掉后台进程），Firefox 也不会为这种情况重新触发 `onStartup`。所以注册一旦被做过一次，只要后台脚本被回收一次，注册就随之消失、不会自动恢复。点一次弹窗「翻译」能让悬浮窗重新出现，只是因为那次点击顺带唤醒了后台脚本、对当前这一个页面做了一次性的 `executeScript`——不是恢复了那条持久注册，换页面或回退自然又没有。

修复：把注册从"只在特定事件里做"改成"这个模块一加载就无条件做一次"。MV3 背景执行环境（Chrome 的 service worker、Firefox 的背景脚本）本就会被随时终止重启，任何需要"活着"的设置就不能只放在某几个事件回调里，必须在模块顶层无条件重做一遍——这是该模型下做持久化设置的标准写法，之前只是没有照着做。见 `src/background/index.ts`、`tests/background-load.test.ts`。


## 13. 学术论文：公式、术语、引用与脚注（2026-10-28，FR-27～29）

### 13.1 公式：占位符发出、原公式放回
行内公式以前被当成"不可翻译的噪音"丢掉，译文里主语和变量都没了。现在公式在发给引擎前换成 `[[1]]`、`[[2]]`，译文回来后在占位符的位置放回**页面上那一份公式的副本**（不解析任何字符串，只复制 DOM 节点，去掉 `id`），所以公式长什么样仍由网页自己决定。选 `[[n]]` 这个写法，是拿谷歌免费接口实测的：`⟦ ⟧` 这类特殊括号会被改成问号，`[[1]]`、`{1}`、`<1>`、`@1@`、`$1$` 都能留住。

占位符偶尔被引擎吞掉一个括号，所以还原时认 `[[3]`、`[3]]` 和带空格的写法；单括号 `[13]` 是参考文献编号，不会被当成占位符。占位符整个丢了时，公式补在句尾，宁可位置不对也不让变量消失。

### 13.2 不翻词表：发出去，再还原
模型名、特殊符号、引用、缩写以 `[[Tn]]` 发出，译文回来后换回原文。规则偏保守：**全大写缩写只在有正文的句子里保护**（整句大写的标题不动）；引用整条保留英文，所以不再出现"Peters et al. 2018a Peters 等，2018a"这种中英各一份。引擎吞掉占位符时，**不把丢掉的词补在句尾**（这样位置不对），而是该句不带占位符重新翻一次，引擎一般会自己保留缩写。

### 13.3 链接与脚注
arXiv 的 HTML 论文里，引用是 `<cite><a>…</a></cite>`，图号是 `<a><span>1</span></a>`，脚注是 `<span class="ltx_note">` 里带一个 `.ltx_note_content` 内容块。整页模式下，"单独的链接是一条条目"这条规则（为了菜单）把引用和图号都切了出去：句子缺了字，译文被插到句子中间。现在判断一个链接是不是"单独的"，要看它外面最近一个**不是格式标签**的容器有没有自己的文字；有，它就是那一句的一部分。`span` 不在格式标签之列，因为网页常用它当布局容器（见"展开/收起"的现有测试）。

脚注一开始按"悬浮提示，不算正文"处理，整块不翻译——这个判断是错的：ar5iv 把脚注排成页面右侧**始终可见**的边注，不是鼠标悬浮才出现的提示，不翻译等于那部分内容永远留着英文（2026-10-29 用户实测发现）。改为：`.ltx_note_content` 和 `.ltx_bibblock` 一样，是它所在段落之外、自己的一条翻译对象；外层的 `.ltx_note`/`.ltx_note_outer` 不再整体排除，只是不被当作候选，所以文字不会被吸收进正文重复一遍。脚注号（`.ltx_note_mark`）仍按上标处理，原样保留。

做完这一步，译文里多出一个孤立的 "1"：脚注内容里有一段 LaTeXML 自带的回链标记（`.ltx_tag_note`），ar5iv 的样式表把它设成 `display: none`——原文看不到，但抽取时从来没检查过"这段内嵌文字是不是看不见的"，只在判断一整个候选段落要不要收进来时查过可见性，候选段落内部按文字走的子元素一直没查。现在逐字遍历时，每个子元素先查是否隐藏，隐藏的跳过，不读、不发、不计数——和读者在屏幕上实际看到的一致。`<math>` 元素不做这项检查，因为它是外来内容，`getComputedStyle` 在上面不可靠（jsdom 环境下会直接抛错），而公式本来就整体按原样复制，不需要这项判断。

再做完这一步，又冒出一个排版问题："…gradients¹. To counteract…" 这种脚注记号卡在句子中间的情况，整句译文被插到了脚注记号前面，脚注记号和句子剩下的半句原文被挤到译文下面单独成行。原因在 `insertionPoint()`：它要在候选元素的直接子节点里找"译文该放在哪"，碰到一个子节点"自己不是候选，但里面有候选内容"时（比如网页自己的"展开/收起"结构：外层是说明文字，后面跟着一段嵌套的详情），就认为这是"容器里还套着一段话"，把译文放在这个子节点前面，确保译文挨着它自己的文字、不跑到嵌套内容后面去。脚注记号现在符合这个特征——它自己不是候选，但 `.ltx_note_content` 是——于是被当成了同一种"容器"，译文被错误地插到脚注记号前面，而不是整句话最后。脚注记号和"展开/收起"的容器是两种性质：后者里嵌着的是这句话自己的延伸内容，前者是挂在某个词后面的旁注，跟这句话的意群无关。修法是在这条判断里专门跳过脚注记号，不当容器处理；脚注本身的翻译继续走它自己的流程，不受影响。

### 13.4 表格：单元格是标签，不是句子
表头和行名（`ESIM+GloVe`、`SST-2`、`QNLI`、`BiLSTM+ELMo+Attn`）单独发给引擎时没有上下文，引擎会"合理地"编出译文（QNLI 变成一座图书馆，ESIM 变成 EXAMPLE）。所以表格里凡是像名字的词都保护起来；整个单元格都是名字时干脆不发送。另外：**译文与原文相同就不显示**，否则 "QQP QQP"、"CoLA CoLA" 这样的重复会铺满整张表。

### 13.5 参考文献：作者不动，标题和刊物翻译
参考文献条目是"作者与年份、标题、刊物"三块。作者名交给引擎只会得到"艾伦·阿克比克"这样的半音译，所以第一块和编号标签不处理；整行斜体的（"arXiv preprint arXiv:…"）是名字，也不处理。标题和刊物行各自翻译，块内的缩写一律保护（否则 "In TAC. NIST." 被翻成"在战术空战术航空站"）。识别靠 LaTeXML 的结构（`ltx_bibitem` / `ltx_bibblock`）；别的网站的参考文献没有这个结构，仍按普通段落翻。

另有一份内置的简体中文术语表（字符级、词级、自注意力、预训练、微调、语言建模…），因为有些词引擎总是翻错，如 Character-level 总被翻成"角色级"；这类词不能靠"首次出现"来锁定，只能写明。

### 13.6 术语整页统一
每段单独送翻，同一个术语出现在五十段里，就被翻五十次，不一定每次一样。办法是：整页找出重复出现的大写开头的多词术语，各翻一次，各段共用。选"大写开头"是因为论文里的术语名（Scaled Dot-Product Attention、Next Sentence Prediction）这样写，而普通名词词组大写的代价是误伤，小写的难以和普通短语区分，所以暂不做。单独翻译的结果如果没变化或失败，就不锁定该术语，让引擎按上下文翻。

### 13.7 没做的
表格单元格、参考文献条目、图表标题"整条翻译，不做段内双语混排"，以及全文术语锁定，见 [24 §2](./24-academic-direction.md)。

### 13.8 行内代码/命令：占位符发出，按文本还原（2026-10-29，FR-36）
句子里的 `npm run build` 这样一句命令写在 `<code>` 里，直接发给引擎翻译会被当成普通文字，常被"本地化"成看不出是命令的样子。办法跟公式一样：换成 `[[Cn]]` 占位符发出，译文回来后按占位符位置放回原文字。两点不同于公式：公式占位符在渲染时克隆页面的 DOM 节点放回去（因为公式本身有格式），行内代码只是文本，所以直接在文本层面替换，和「不翻词表」(FR-28) 的术语占位符走同一条还原路径（只是前缀是 `C` 不是 `T`，互不干扰）；公式和术语的占位符本身在保护阶段会被跳过不处理，行内代码占位符同理。只有行内 `<code>/<kbd>/<samp>/<var>/<tt>`，`<pre>` 代码块仍整体不翻——块级代码里挑出注释单独翻译需要按语言识别注释语法（`//`、`#`、`/* */`、`<!-- -->`…），风险是误伤字符串或正则里长得像注释的内容，这次没做，见 [25 §1.1](./25-plan-progress-and-open-core.md)。

### 13.1 第一次实际使用后的三处修正和一项新增（2026-10-31）

- **翻译前后 logo 看不出区别**：原计划只靠 `aria-label` 区分状态，实机一看发现不够——视觉上完全看不出"已经翻译过"。加了一个小圆角对勾徽标，贴在主按钮右下角，`translated` 为真时才显示，翻译中（转圈）时隐藏，不与状态图标混在一起。
- **悬停动画太弱**："细微"的程度到了几乎看不出来。换成一个一次性的小弹跳动画（`logoPop`：缩放带一点旋转），每次鼠标移进去都重新播放一遍，比单纯放大更有"动感"。
- **真 bug：离开鼠标后齿轮不消失**：点一下主按钮翻译/取消翻译之后，齿轮的悬停显示用 `:focus-within` 兜底键盘可达性，但按钮点击后会保留浏览器焦点，`:focus-within` 就一直为真，鼠标挪开也不会消失，直到点页面别处夺走焦点才行。改法是点击处理完之后显式 `ball.blur()`——键盘 Tab 导航仍然能通过 `:focus-within` 看到齿轮，只是鼠标点击这条路径不再卡住它。
- **新增"自动翻译当前网站"开关**：复用设置页"自动翻译的网站"那份名单（`autoTranslateSites`），但**开**和**关**走两条不同的路——关闭只是收回权限，`chrome.permissions.remove` 不需要用户手势，可以直接从内容脚本经消息发给后台处理；**开启需要申请新权限**，而 `chrome.permissions.request` 只认发生在扩展页面（弹窗/设置页）上的真实用户手势，内容脚本的点击不算数，经后台转发也不算数——这不是没试对手势时机，是 Chrome 对这个 API 的硬限制。所以"开"这个方向改成打开设置页、把当前网站名**预先填好**，用户只需要在那边点一下"添加"，免去手动输入，但省不掉那一次在扩展页面上的真实点击。

### 13.2 已授权"所有网站"时不再跳转；朗读加了快捷按钮（2026-10-31）

- **"已经允许所有网站了，还要我跳一次设置页？"**——问得对。打开"自动翻译当前网站"这件事本身不一定需要新权限：如果读者已经开了"允许在所有网站上运行"，这个网站的访问权限早就有了，根本不用再申请。改法是后台先查一次 `chrome.permissions.contains`（这一步不需要用户手势，纯粹是查询），查到已经覆盖就直接把网站加进名单、不跳转；查不到才退回"打开设置页、预填网站名"那条路。关闭仍然不用查，随时能直接做。
- **朗读加了快捷按钮**：放在齿轮正下方，图标是个小喇叭（朗读中换成一个打叉的喇叭），点一下直接朗读/停止朗读，不用先点齿轮展开面板。可见性跟齿轮一致（鼠标悬停才出现，触屏常驻），翻译前（没什么可读时）不显示。

回归测试：`tests/background-load.test.ts`（权限分支）、`tests/floating.test.ts`（快捷按钮）。

### 13.3 齿轮和朗读快捷键合并成一个胶囊（2026-10-31）

两个独立的小圆点看着是两个不相关的东西；改成一个白色圆角胶囊，齿轮在上、朗读在下，中间一条细分隔线——悬停/触屏常驻这条可见性规则现在挂在胶囊整体上，不再分别挂在两个按钮上，一起出现一起消失。朗读按钮在没有译文可读时仍然隐藏，这时胶囊里只剩齿轮一项，圆角照常收边，不会露出一截空的分隔线。
